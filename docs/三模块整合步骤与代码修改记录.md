# 三模块整合步骤与代码修改记录

本记录以本仓库当前源码和《大型平台软件设计实习》指导书、三个模块根目录规约为依据。整合时保留了全部原有文件；新增代码集中在数据库引擎的 `api/` 和 `integration/` 目录，其余仅修改接口边界、构建和测试所必需的已有文件。数据库引擎核心仍通过 `SqlCompilerClient`、`PageStorageClient` 两个接口工作。

另修改根目录 `.gitignore`：继续忽略 `docs/` 中原有大型原始材料，但明确放行本记录文件，以便该交付文档能随仓库提交。

## 1. 建立统一构建与跨平台启动入口

1. 新增仓库根目录 `pom.xml`，以 Maven reactor 按 `sql-compiler` → `page-storage-system` → `database-engine` 的依赖顺序构建三个原有模块；没有迁移任何源码目录。
2. 修改 `database-engine/pom.xml`：增加两个组内模块依赖，保留 Java 17、Jackson、JUnit 配置；由 Maven Shade 在 `package` 阶段生成包含全部运行依赖的 `database-engine/target/chainpage-db.jar`，主类为 `ChainPageMain`。
3. 新增 `ChainPageMain.main(String[])`：解析 `--data 数据目录`、`--format human|json`、`--json`、`--file SQL文件` 和 `--help`，打开数据库，按 UTF-8 从标准输入或 SQL 文件读取请求，默认以 MySQL 风格文本输出，显式以 UTF-8 输出响应和错误，在正常退出时关闭数据库。文本交互模式使用 JLine 提供光标编辑，启动后显示欢迎信息，每次输入前显示 `cpdbs>`；JSON模式保持纯JSON行输出，文件模式不显示交互式提示符。路径使用 Java `Path`，不依赖 shell 或系统特定分隔符。
4. 修改 `DatabaseCli.handleLine(String)`：保留原有每行 JSON 请求方式，同时允许直接输入一整行 SQL；`EXPLAIN` 仍走只生成计划、不执行写入的专用分支。
5. 修改 `DatabaseApi.handleExecute(String,DatabaseRequest)`：拒绝直接通过 `execute` 模式提交的 `EXPLAIN`，要求调用只读 `handleExplain`；防止 Java API 绕过 CLI 分流后意外执行 `EXPLAIN UPDATE` 等写计划。

从仓库根目录可以直接使用新增的一键脚本（Windows、macOS、Linux）：

```text
# macOS / Linux
./run.sh
./run.sh --file demo.sql

# Windows cmd.exe
run.cmd
run.cmd --file demo.sql

# Windows PowerShell
.\run.ps1
.\run.ps1 --file demo.sql
```

脚本发现 `database-engine/target/chainpage-db.jar` 不存在，或源码和 POM 比 JAR 更新时，会自动运行 `mvn -DskipTests -pl database-engine -am package` 构建可执行 JAR；macOS/Linux使用 `run.sh`，Windows使用 `run.ps1`（`run.cmd`会优先转交给它）。也可以继续手动运行 `mvn package`。直接使用 JAR 的完整命令仍然有效：`java -jar database-engine/target/chainpage-db.jar --data chainpage-data`。

Windows `cmd.exe` 也可用以上命令；若 shell 不接受 `/` 路径，可改用 `database-engine\target\chainpage-db.jar`。运行后每行输入一条完整 SQL，例如 `CREATE TABLE student(id INT, name VARCHAR);`、`INSERT INTO student(id,name) VALUES (1,'Alice');`、`SELECT * FROM student;`；输入 `quit` 退出。默认输出为文本：查询显示带边框的表格，建表/增删改显示 `Query OK, N rows affected`，错误显示 `ERROR code (stage): message`。需要脚本处理时可追加 `--format json`（或 `--json`）恢复原统一JSON包络。也可输入一行 JSON 请求：`{"sql":"SELECT * FROM student;","mode":"execute"}`；`mode` 可换成 `compile` 查看计划摘要。数据目录可换成任意该用户可写的路径；再次以相同 `--data` 路径启动即读取持久化内容。

文本交互模式启动后会显示启动提示和 `cpdbs>`，可用左右键编辑当前命令、上下键浏览本次会话历史、Ctrl+C取消当前行。默认文本输出查询表格、`Query OK, N rows affected` 和 `ERROR code (stage): message`。需要脚本处理时可追加 `--format json`（或 `--json`）；JSON模式不输出启动提示和命令提示符，以保证每行都是一个JSON对象。JSON输入请求仍可使用 `{"sql":"SELECT * FROM student;","mode":"execute"}`，`mode` 换成 `compile` 可查看计划摘要。

使用 `--file demo.sql` 时，入口按 UTF-8 读取文件，按照 SQL 分号拆分语句，并忽略字符串、`--` 单行注释和 `/* ... */` 块注释中的分号；因此一条 SQL 可以跨多行书写。文件中的 `quit` 或 `exit` 会提前结束批处理。人类可读模式仍会显示一次启动提示，但不会显示 `cpdbs>`；配合 `--format json` 时标准输出只包含每条语句的 JSON 响应。

## 2. 接入真实 SQL 编译器

新增 `CompilerModuleClient`，实现引擎原有 `SqlCompilerClient`，并不改写 SQL 编译器内部结构：

- `compile(CompileRequest)`：将引擎目录快照变成编译器接受的 JSON 对象，调用 `CompilerFrontEnd.compile`，把成功响应还原成 `CompileResponse`，检查 `requestId` 是否一致。
- `explain(CompileRequest, Map)`：把 `EXPLAIN` 请求交给编译器 `ExplainService`，构造只供引擎 `ExplainService` 展示的 `CompiledStatement`，不交给执行器。
- `error(Map,String)`、`integer(Object)`、`invalid(String,String)`：保留编译器给出的阶段、错误码、语句序号、行列位置，并对格式错误响应给出明确错误。

目录快照来自真实 `SystemCatalogManager`，因此建表后下一次编译与重启后的编译使用同一份持久化表结构。

## 3. 接入真实页式存储

新增 `PageStorageModuleClient`，实现引擎原有 `PageStorageClient` 的七个操作：`getPage`、`writePage`、`createTablePages`、`dropTablePages`、`allocatePageForTable`、`listTablePages`、`flushAll`。每个方法调用页式存储模块公开的 `StorageCli.handle(StorageManager,Map)` 操作，统一传入 `requestId`，将响应转换为引擎 DTO。内部 `call` 校验 `ok`、`data`、`requestId`，`error` 传递页号和错误码。执行器仍不直接操作磁盘文件、缓存或页映射。

新增 `ChainPageDatabase` 负责唯一的生产组装顺序：创建 `StorageManager` → 页客户端及事务感知包装 → `StorageEngine` → 持久化系统目录 → 注册全部核心/扩展执行器 → 恢复与生命周期 → 编译器客户端 → `DatabaseApi`、`DatabaseCli`。`executePlan` 解析和执行编译计划；`shutdown`/`close` 先刷新页再关闭存储。`transactions()` 和 `authorization()` 暴露共用页客户端、执行器和目录的事务/授权服务，供 Java API 调用；它们不是 SQL 语句。

## 4. 修复跨模块计划字段不一致

真实编译器对排序、分组和多表连接使用 `表名或别名.列名`，存储记录则保存表内列名。本次修改在执行边界完成映射：

- `SeqScanExecutor.execute` 新增 `bindPlanSchema`：逐列核对编译计划与物理表的列名、类型、顺序，将实际行值绑定到计划里的限定列名。这样 `Sort`、`Filter`、`GroupBy`、`Join` 消费同一套计划列名，且不污染物理表记录。
- `ExpressionEvaluator.evaluateIdentifier`：优先使用编译器表达式 `binding.table` 与 `binding.column` 读取限定列，未绑定的原有计划继续按裸列名读取；修复 `WHERE` 与扩展排序组合时的错误列引用。
- `ProjectExecutor.execute`：投影取值仍按编译计划 `columns`，对编译器限定列或聚合别名则使用输出 `schema` 的用户可见列名；原有手写计划的显式列顺序保持不变。
- `PlanParser.parseSchema`：允许聚合中间结果 `BIGINT`；物理建表类型约束仍由原有建表/记录校验执行，不能因为中间结果类型而放宽磁盘表的 `INT`/`VARCHAR` 规约。
- `GroupByExecutor.group`：将聚合数值的中间行集类型标为 `BIGINT`；`SortExecutor.matchesType` 接受该类型的数字排序。

这些改动使真实编译器产生的 `UPDATE`、`ORDER BY`、`GROUP BY COUNT`、等值内连接计划可由现有扩展执行器实际执行，而不是仅各模块独立单测通过。

## 当前边界

- 物理表类型按 `database-engine-spec.md` 保持 `INT`、`VARCHAR`；SQL 编译器单独支持的额外类型、`NULL` 三值逻辑等并未变成物理数据库能力，不能将编译器单测等同于三模块能力。
- `IndexScan` 保留原规约的索引不可用错误和顺序扫描回退边界；目前没有 `CREATE INDEX`/索引持久化 SQL 接口，不应宣称已有实际 B+ 树索引。
- 事务与授权由 `ChainPageDatabase.transactions()`、`authorization()` 提供 Java API；命令行 SQL/JSON 请求尚未定义事务会话命令格式，不能将普通 SQL 自动视为显式事务。
- 已在本机 macOS 上执行构建和 JAR 端到端验证。启动方式使用 Java 17/Maven 与系统无关的命令，但本次工作区没有 Windows 或 Linux 主机，因此这两种系统没有实机验收记录。
